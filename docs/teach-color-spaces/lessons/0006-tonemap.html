Color Spaces & the Fold Pipeline · Lesson 6 · finale

Tonemap

The final linear → screen arrow — and why your compositor pins it to "Linear."

One arrow left. The fold is done, decoded back to linear (Pass C), and the frame is sitting in the linear scene buffer — still HDR, still linear. The monitor can't show that. Tonemap (Pass 5) is the step that makes it displayable. Question 7 — what is a tonemap? — plus the one constraint your design stamps on it: it must be Linear.

1 · What a tonemap does

The linear scene is HDR: values run [0, ∞) — a sunlit highlight might be 8.0, an emissive core 40.0. A monitor accepts only [0, 1], gamma-encoded. Tonemap bridges that gap in two moves:

• Tone mapping (the operator): compress the open-ended HDR range down into [0, 1] — decide how highlights roll off, how the midtones sit.

• Encode to screen: apply the sRGB curve (linear → gamma) so the monitor shows the right brightness (L1). This is the linear → screen arrow from Lesson 5.

"Which operator" is a creative/technical choice, and Godot offers several:

OperatorCurveEffect
Linearidentity (+ exposure/clamp) No reshaping. Values ≤ 1 pass through untouched; > 1 clip. Then sRGB encode.
Reinhardx/(1+x)Smoothly compresses highlights; never clips.
Filmic / ACES / AgXS-curve (toe + shoulder) Film-like: lifts blacks, rolls off and desaturates highlights, shifts contrast/hue.
Operator reference: GDQuest — Tonemap and Godot — High Dynamic Range. The operator lives on the Environment, not per-material.

2 · Why the fold demands Linear

Your compositor's header is blunt about it — CombatDisplaySpaceComposite.gd:36:

## Run under Linear tonemap (ACES/AgX corrupt the add).

Here's why, using everything you now know. By the time tonemap runs, the fold has already produced the exact final PSX colors — authored 5-bit palette colors, added in gamma, in order (Lessons 4–5). They are finished. They just need to reach the glass unchanged.

The corruption An S-curve operator (ACES/AgX) doesn't pass colors through — it reshapes them: it lifts blacks, rolls off highlights, and desaturates as things get bright. Run it on the fold and your crisp additive white core comes out dimmer and grayer; your saturated PSX colors shift hue. The carefully-built additive result gets a film look stamped on top of it. That's the "corrupt the add."

AgX is the worst offender — it's designed to desaturate highlights hard, which is exactly where additive PSX effects live. Linear is the only operator that applies no reshape: values ≤ 1 pass straight through (then sRGB-encode), so the authored colors land on screen as authored.

3 · The elegant part: why the detour to linear is free

You asked earlier why Pass C bothers decoding back to linear if it's "just going to be gamma again." Now it closes. Watch a folded pixel through the last two passes:

Pass C: fold result display ──decode──▶ linear Pass 5: linear ──Linear-tonemap encode──▶ screen decode (display→linear) then encode (linear→screen) with the SAME curve = identity re-encode

Because display and screen are the same space (your Lesson-1 payoff), and Linear tonemap doesn't reshape, the decode in Pass C and the encode in Pass 5 are inverses that cancel. The folded color you built in the scratch reaches the monitor essentially unchanged.

So why detour through linear at all? So that folded pixels and the untouched HDR background flow through one shared output path. The background genuinely needs tonemapping (it's linear HDR); the fold pixels ride the same pass and, thanks to Linear, pass through untouched. Swap in ACES and you'd wreck both the fold (reshaped) — which is why the constraint exists.
