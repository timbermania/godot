Color Spaces & the Fold Pipeline · Lesson 2

Who's in front? The depth buffer

What it is, when it's written — and how your fold prims get occluded by walls they never share a pass with.

Lesson 1 was about what a color number means. This lesson is about a second buffer that rides alongside the color buffer and answers a different question: at each pixel, which surface is nearest the camera? Get this, and question 3 from your list — "how do the blend prims get a depth buffer even though they aren't in the opaque scene?" — stops being mysterious. The answer is that they don't, and that's exactly why it works.

1 · What the depth buffer is

The depth buffer (a.k.a. z-buffer) is a second image, same resolution as the screen, holding one number per pixel: the distance to the nearest surface drawn there so far, encoded 0 → 1 (near → far). It exists to solve occlusion without sorting geometry on the CPU.

The mechanism is the depth test, run per fragment as things rasterize:

incoming fragment at pixel P, with depth z
  if z is nearer than depthBuffer[P]:
      keep the fragment        (draw its color)
      depthBuffer[P] = z       (record the new nearest)
  else:
      discard the fragment     (something already covers P)

Draw a wall, then draw a unit behind it in any order — the buffer sorts it out per pixel. That's the whole reason opaque 3D scenes don't need back-to-front sorting.

Primary source for this section: LearnOpenGL — Depth testing. Covers the z encoding, the test, and z-fighting (what happens when two surfaces round to the same depth).

2 · The insight: test and write are two separate switches

This is the part that unlocks everything. Every material has two independent depth controls, and people conflate them constantly:

Depth TEST  (read)

"Compare my z against the buffer, and discard me if I'm behind." Decides whether this fragment is occluded.

Depth WRITE  (draw)

"Record my z into the buffer so I occlude whatever comes after me." Decides whether this fragment occludes others.

They're orthogonal — any combination is legal. Godot spells them out as render_mode flags, and your FFT codebase uses three combinations, each on purpose:

render_modeTest?Write?Meaning · real example
depth_draw_opaque yesyes Normal solid geometry. Occludes and is occluded.
unit.gdshader (the opaque unit).

unit_additive.gdshader, tile_overlay_mode0.gdshader.

3 · Q2 — when is the depth buffer written?

During the opaque pass (Pass 1 of the diagram). Opaque units are depth_draw_opaque, so as they rasterize they stamp their z into the depth buffer. By the time the opaque pass ends, the depth buffer holds the nearest opaque surface at every pixel — the map, the walls, the standing units. Nothing in the seed / fold / out / tonemap passes writes depth; it's already done.

4 · Q3 — how do the blend prims get depth without being in the opaque scene?

The answer They don't get their own depth. The fold binds the opaque pass's already-written depth buffer, read-only, and the prims depth-TEST against it with depth-WRITE off. So walls occlude the prims, but the prims neither add to nor disturb the depth buffer.

Your own shader comments say it outright. The additive unit:

// depth_draw_never: an additive, dematerialising sprite must not write opaque
// depth (it still depth-TESTS against the map, so walls occlude it correctly).
render_mode unshaded, shadows_disabled, depth_draw_never, blend_add;
                                        //  ^ test ON (default), write OFF

Spike 1 confirmed this on the GPU: an additive prim placed behind an opaque wall read back 0.0 — fully rejected by the test. It never appeared, despite living in a totally separate render list from the opaque scene. The depth buffer doesn't care which pass or list a fragment came from; the test just reads the numbers that are already there.

The consequence that matters for your design

Because none of the fold prims write depth, they can't occlude each other. The tile_overlay comment nails it:

// depth_draw_never: still depth-TESTS against terrain via the OT depth we write,
// but doesn't depth-WRITE, so overlapping tiles don't occlude each other.

So depth decides prim-vs-world, but it does not decide prim-vs-prim. That ordering has to come from somewhere else — and it does: the draw order, which is precisely what OTDepthPrimOrder controls (the "age within a depth bucket" sort in your plan). Depth-test handles occlusion; draw order handles blend order. Two different jobs, cleanly separated. We'll open up that sort in a later lesson.

Contrast the third row: screen_color_mode0.gdshader adds depth_test_disabled — its comment, "depth_test_disabled makes z irrelevant (always on top)." That's a fullscreen overlay that should ignore the world. The fold prims deliberately do not disable the test — they want the walls to occlude them.

5 · Keyed to the passes

Pass 1  opaque     WRITE depth  ── units are depth_draw_opaque
Pass A  seed       (depth untouched)
Pass B  fold       TEST  depth  ── prims depth_draw_never: test vs opaque, no write
Pass C  out        (depth untouched)
Pass 5  tonemap    (depth untouched)

One buffer, written once in Pass 1, read once in Pass B. That single read is the entire mechanism behind "the prims are correctly hidden by walls."
