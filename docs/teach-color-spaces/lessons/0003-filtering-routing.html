Color Spaces & the Fold Pipeline · Lesson 3

The filter: who's opaque, who gets folded

How a material's render settings route it to the opaque pass, the normal transparent pass, or your fold — decided once per surface, per frame.

Question 4 on your list: "How are we filtering what does and does not get rendered in the opaque scene?" The short answer: the engine sorts every surface into a render list based on its material's render settings, and the opaque list is one of them. Nothing "decides to be opaque" at runtime — it's a static property of the material, read once as the render lists are built. And the best part: it's not a black box. It's on this branch, and we'll read the actual lines.

1 · Two levels of filtering

There are exactly two decisions, in order:

Level 1 — opaque or transparent? Godot's built-in split. Determines the OPAQUE list vs. the transparent (ALPHA) list.

Level 2 — normal transparent, or folded? Your Spike-1 engine change. Among the transparents, peel off the ones flagged compositor_fold into a separate fold list.

2 · Level 1 — the opaque/transparent split is one function

When the engine builds a surface's cache, it asks the material a single yes/no question — uses_alpha_pass() — and sets one flag. Here is the real function on this branch (scene_shader_forward_clustered.h:283):

bool uses_alpha_pass() const {
    bool has_alpha       = uses_alpha || uses_blend_alpha || has_read_screen_alpha;
    bool no_depth_draw   = depth_draw == DEPTH_DRAW_DISABLED;   // render_mode depth_draw_never
    bool no_depth_test   = depth_test != DEPTH_TEST_ENABLED;    // render_mode depth_test_disabled
    return has_alpha || has_read_screen_alpha || no_depth_draw || no_depth_test;
}

Read it as a rule: a material is transparent if any of these is true —

ConditionTriggered by
uses_alphathe fragment writes ALPHA < 1 (real translucency)
uses_blend_alphaa non-mix blend — blend_add / blend_sub / blend_mul
no_depth_drawrender_mode depth_draw_never
no_depth_testrender_mode depth_test_disabled

Otherwise — none of those — it's opaque, and the engine also stamps it FLAG_PASS_DEPTH so it writes into the depth buffer. That last part is literally the same decision as "who writes depth in Pass 1" from Lesson 2: opaque ⇒ depth prepass ⇒ writes z.

The connection to Lesson 2 Look at the last two conditions. Turning off either depth switch — depth_draw_never or depth_test_disabled — is by itself enough to make a material transparent. That's why your fold prims are never in the opaque scene: an additive unit (blend_add, depth_draw_never) trips three of these conditions at once. The "depth" lesson and the "filter" lesson are the same switches seen from two angles.

3 · Level 2 — the fold split (your engine change)

Once Level 1 has tagged a surface FLAG_PASS_ALPHA, the render-list loop decides which transparent list it joins. This is the code Spike 1 added (render_forward_clustered.cpp:1146–1160):

// opaque surfaces → the opaque render list
if (surf->flags & (FLAG_PASS_DEPTH | FLAG_PASS_OPAQUE)) {
    rl->add_element(surf);
}

// transparent surfaces → split by the compositor_fold flag
if (surf->flags & FLAG_PASS_ALPHA) {
    if (surf->shader->compositor_fold) {
        render_list[RENDER_LIST_COMPOSITOR_FOLD].add_element(surf);   // your fold list
    } else {
        render_list[RENDER_LIST_ALPHA].add_element(surf);             // normal transparent
    }
}

And the flag itself is a first-class render_mode, registered in shader_types.cpp:245 with the comment "route this material's shaded transparent output into the compositor fold scratch buffer." A material opts in just by writing render_mode … compositor_fold; — it still shades through its real pipeline; the engine only retargets where the result lands.

4 · The whole filter, in one tree

every surface, once per frame │ ├─ uses_alpha_pass() == false ──▶ RENDER_LIST_OPAQUE (Pass 1 · writes depth) │ └─ uses_alpha_pass() == true (has alpha, or add/sub blend, or a depth switch off) │ ├─ shader.compositor_fold == true ──▶ RENDER_LIST_COMPOSITOR_FOLD (Pass B · your fold) │ └─ shader.compositor_fold == false ──▶ RENDER_LIST_ALPHA (normal transparent)

Three destinations, two questions, both answered from the material alone. Your standing units (unit.gdshader, opaque) take the top branch — "free" in the opaque scene, writing depth for everyone else to test against. The flagged additive/sub/mix prims take the middle branch into the fold. Ordinary transparents (an unflagged HUD blend) take the bottom.

The fold list is then sorted by sort_by_priority(), not by depth — the comment on render_forward_clustered.cpp:1928 says it outright: "fold in the CALLER's order (render_priority = OTDepthPrimOrder run index), NOT camera depth." That's the draw-order hook Lesson 2 promised — the prims don't self-occlude, so their blend order comes from this sort. We'll open it fully in a later lesson.

5 · Keyed to the passes

The filter runs before any drawing — it's the list-building step that feeds the passes:

build render lists   ── the filter above runs here (per surface)
Pass 1  opaque       ── draws RENDER_LIST_OPAQUE,          writes depth
Pass A  seed         ── (compositor)
Pass B  fold         ── draws RENDER_LIST_COMPOSITOR_FOLD, ordered, into the display scratch
Pass C  out          ── (compositor)
        + normal transparent draws RENDER_LIST_ALPHA as usual
