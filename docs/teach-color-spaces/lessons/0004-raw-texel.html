Color Spaces & the Fold Pipeline · Lesson 4

The raw texel

Where Lesson 1 meets the fold: the color space isn't in the blender — it's in the numbers you feed it.

You now have the two halves. Lesson 1: numbers are either linear or gamma. Lessons 2–3: which surfaces reach the fold, and why. This lesson joins them by answering question 6 — what is a raw texel? — and through it, the load-bearing insight of your entire design: a hardware blend has no color space of its own; it inherits the color space of the numbers going in.

1 · A texel, and what Godot normally does to it

A texel is one sample read from a texture — the value at a texture coordinate. Nothing exotic.

The subtlety is what happens on the way out of the sampler. In Godot, if you declare a color texture with source_color (the sRGB hint), the GPU decodes it sRGB → linear as you sample it. That's deliberate and correct: it drops your texel into linear space so the lighting math (Lesson 1) is right. Most color textures in a 3D scene work exactly this way.

2 · A "raw" texel is one sampled with no such conversion

Definition A raw texel is a texture sample taken without source_color — so Godot applies no sRGB → linear conversion. The stored bytes come out verbatim, in whatever encoding they were authored in.

Your PSX unit atlas is sampled exactly this way. From unit_sprite_body.gdshaderinc:640:

// No source_color - PSX textures are not sRGB. We convert to linear at the end.
uniform sampler2D type1_tex :
    filter_nearest,
    hint_default_transparent ;      // <- note: no source_color

Why raw here? Because this texture isn't a picture — it's a table of palette indices. The comment at line 657 spells it out: "an indexed-grayscale TGA (each pixel = palette index 0–15 scaled to 0–255)." A value like 153 means "palette entry 9," not "60% bright." Two consequences, both visible in that sampler declaration:

• filter_nearest — never bilinear-blend indices (averaging index 3 and index 9 gives index 6, a garbage color).

• no source_color — never sRGB-decode an index (it isn't light; the math would be meaningless). You need the exact stored byte to look up the palette.

3 · Indices don't get added — colors do

Here's the ordering that (rightly) trips people up: the raw index never reaches the blender. Inside the fragment, the index is resolved to a real color first, and only that color is added. From unit_sprite_body.gdshaderinc:510–525:

float idx_f = texture(tex, uv).r * 15.0;              // 1. raw index  (grayscale byte → 0–15)
...
vec4 color = texture(palette_tex, palette_uv).rgba;  // 2. palette lookup → a real RGBA color
...                                                  // 3. tint / ambient → ALBEDO
// 4. the hardware ADD runs OUTSIDE the shader, on the resolved ALBEDO — never on the index

You do not add indices — that would be meaningless. Palette lookup happens in step 2; the blend happens in step 4, after the color is applied. So there are two independent uses of "no source_color," doing different jobs — don't conflate them:

WhereWhat "no source_color" buys
the index texture (type1_tex) — plus filter_nearest protects the lookup key (an index isn't light — decoding or blurring it corrupts the lookup). Nothing to do with color space.
the palette texture (type1_palette) the resolved color comes out in the palette's stored display encoding, un-linearized. This is what makes the later ADD a gamma add.

"Raw index" and "display-space color" are different links in the chain, with the palette lookup between them. What the blender adds is the resolved color — and it's a gamma add iff that color is a gamma number, which it stays as long as neither the palette sample nor a final pow linearizes it.

4 · The load-bearing insight: the blend has no color space

Here is the sentence your whole architecture rests on, from engine-shaded-display-fold.md §3:

The insight The hardware blender is color-space-agnostic. BLEND_OP_ADD computes dst + src on the raw numbers in the attachment — it has no notion of linear vs. gamma. A blend is a gamma-space blend iff both operands hold gamma numbers — regardless of who issues the draw.

So "blending in display space" is not a mode you switch on. It's what you get when both inputs are display numbers. Your compositor's fold fragment says this in its own words (combat_displayspace_composite.glsl:258):

// The sprite texel is raw sRGB/display (the mode shaders declare NO source_color),
// so the contribution stays in DISPLAY space; the blend adds it to the display-space
// scratch ... gamma is intentionally unused — linearizing the texel IS the defect
// this compositor removes.

Read that last clause slowly, because it's the punchline. The defect the compositor exists to fix is linearizing the texel. Keep the resolved color un-linearized (display), add it to a display scratch, and the hardware ADD is automatically a gamma add — the PSX look — with no special blend mode. The color space rode in on the data.

5 · The honest caveat (this is exactly your open question #1)

"Raw texel" describes the input sample. Whether the fragment's output is still display depends on what the shader does at the very end — and here the files disagree in a way the plan flags as unresolved.

Read the two files side by side

The compositor's particle/mode fold shaders sample raw and never re-encode — output stays display. The gamma fold works today.

The real unit material samples raw too — but at unit_sprite_body.gdshaderinc:923 it ends with ALBEDO = pow(ALBEDO, 2.2): it decodes to linear "for Forward+." So the shipped unit fragment outputs linear, not display.

That final pow is the right thing for the unit's normal job — an opaque unit in Pass 1, where the scene is linear (Lessons 2–3). But it is literally the "defect" the compositor's comment calls out. So the plan's phrase "the prims emit raw display texels" is:

• true today of the compositor's hand-ported particle fold, and

• a target, not yet guaranteed, for the engine drawing the real unit material into the fold — because that material would first have to not run its line-923 linearization.

This is precisely open question #1 in engine-shaded-display-fold.md §7: "Raw-value preservation — PROTOTYPE FIRST. Does the engine's fragment→scratch write preserve raw display values…?" You don't need to solve it now — but you can now say exactly why it's open, from the two files, instead of taking the plan's word for it. That's the whole point of this course.

6 · Keyed to the passes

Pass 1 opaque sample raw index → palette → pow(2.2) → LINEAR (correct: Pass 1 is linear) Pass B fold sample raw index → palette → NO re-encode → DISPLAY (so the ADD is a gamma add) └─ open Q1: make the engine-drawn real material take THIS branch, not the pow one

Same raw texel in both. The difference that decides the color space is a single line at the end of the fragment. That's "the color space lives in the data," made concrete.
